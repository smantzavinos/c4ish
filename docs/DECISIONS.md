# c4ish — design decisions

A dated log; later entries can supersede earlier ones. See [`DESIGN.md`](DESIGN.md) for the current design.

## 2026-10-21 — Founding decisions

1. **Purpose: review of a planned change.** The primary user is a human approving a proposed change quickly. Agents author models; humans read diagrams.
2. **Versioned JSON is canonical.** Diagrams are rendered from the model. A hand-edited diagram is never the source of truth. Layout adjustments live in a separate sidecar file, not in the model.
3. **C4-inspired, not C4-strict.** Levels go beyond C4: system → container → component → data → field. Libraries used inside a component are first-class.
4. **Product and engineering in one model.** One change can show what changes for the user and how it is built, as two views with a mapping between them.
5. **Notation carries meaning, and is data.** Projects define element types, relationship kinds, enforcement levels and visual notation in a profile. c4ish ships a generic default. Core rules: structure is nesting, reference is a connector; every connector states its enforcement; line style carries meaning without colour; colour means one thing per view.
6. **Change state everywhere.** New, modified, reused and removed are core, not decoration. Removed items stay visible.
7. **Patterns are references, not content.** An element names its project pattern (type/variation). c4ish links to the catalog but doesn't store pattern content.
8. **Throwaway models.** A model is scoped to one change. No whole-system inventory.
9. **Rendering and layout first; model editing later.** v0 renders, auto-lays out and lets the user adjust the layout. Editing the model in the viewer is deferred.
10. **Library-first, single repository.** Svelte 5 + TypeScript library with a small SvelteKit viewer in `src/routes`, a CLI for agents, Nix for tools, pnpm for dependencies.

## 2026-10-21 — Phase 1 (v0 implementation)

11. **ELK first, TALA later.** Layout goes through a `LayoutEngine` interface (`src/lib/layout/types.ts`). It returns absolute rects, edge polylines and label boxes. v0 ships an elkjs implementation: layered, `INCLUDE_CHILDREN` for compound nodes, orthogonal routing, fixed-side ports for fields, inline edge labels. elkjs is pure JS, so it builds reproducibly and runs in Node and the browser. A TALA adapter and pinned positions (`LayoutNodeInput.fixed`) fit the same interface. Supersedes "TALA is the first candidate" in DESIGN §4.
12. **Pure-TypeScript SVG renderer, no headless browser.** The renderer emits an SVG string and doesn't depend on the DOM. The CLI, tests and the SvelteKit demo all use the same code (`{@html}` in Svelte). This answers PLAN open question 3. Svelte components for an interactive viewer can wrap the same scene later.
13. **Deterministic text metrics.** Text is measured from Noto Sans advance widths baked into `src/lib/text/metrics.ts` (generated from `@fontsource/noto-sans`), with a 3% safety margin. The font stack is `'Noto Sans','Inter','Segoe UI',system-ui`. The same model gives byte-identical SVG on every machine (tested).
14. **Change state is hue-free.** New = ink header band; modified = light slate band; reused = muted; removed = dashed grey with strikethrough. Each also gets a text badge. Hue is left for the one per-view meaning (enforcement or area). See VISUAL_SPEC §4.1.
15. **Only data relationships are coloured by enforcement.** Runtime calls are quiet slate even when the model states an enforcement level. Colouring every connector amber made "our code" the dominant colour and hid the few relationships that carry integrity. Lint still requires enforcement on data kinds (`enforcementRequired`).
16. **Top-down by default for engineering and product views.** In layered left-to-right layouts, real models came out 3–4× wider than tall. Top-down reads as a page: UI, then backend, then data, with notes beside it. Views can still set `direction`.
17. **Text is split into title / subtitle / details.** Titles have a budget of 40 characters and subtitles 64 (lint). A subtitle wraps to two lines. Details become lettered footnotes, and contracts become C1… footnotes. Nothing is lost, and the diagram stays scannable.
18. **`include` means "these subtrees".** A listed element brings in its ancestors (as frames) and its descendants. `exclude` removes subtrees; element-level `views` restricts further.

## 2026-10-21 — Phase 2 (visual iteration and viewer)

19. **Card colour = pattern, line colour = who enforces.** The owner could not tell patterns apart from a glyph and a chip. Engineering views now use two separate hue channels: the card (header tint, 7px left band, icon, caps pattern label) takes `PatternDef.colour`, falling back to the family colour; data connectors keep the enforcement colours. Pattern colours avoid rose and amber, which belong to enforcement. Proposed patterns keep the hatch (band and header). The key states both mappings in words. Lint `colour-meaning` now only warns about a *pattern* + *relationship kind* pair, which really does compete for hue. Supersedes "hue for patterns by default" in VISUAL_SPEC §10 and refines 14.
20. **Change state lives on the badge and border, not the header.** The header belongs to the pattern now. New gets a solid ink badge and a 1.5 ink border; modified gets an outlined badge; reused is drawn at 50% opacity with a thin grey border; removed is dashed slate, struck through, with a solid badge. Reused context recedes, so changes, proposals and risks stand out. Still hue-free (14).
21. **Diagram-first page.** The page holds the title, review focus, diagram, and a right column with numbered notes and a compact key. Details and contracts are no longer printed as footnotes. `render --appendix` writes `<out>.appendix.md` (notes, lettered details, connector details, contracts), and the viewer shows them in a side panel. Fonts are larger (node title 14.5, label 11.5). Supersedes the footnote half of 17.
22. **We place connector labels after routing; `direction: 'auto'`.** ELK routes without labels. `placeLabels` then tries positions along each polyline (on the line or beside it) and penalises overlap with cards, frame headers, other labels and crossings. If labels still collide, the layout is retried with more layer spacing. `direction: 'auto'` (the default profile) lays out top-down and left-to-right and keeps the lower `layoutScore` (bends, length, aspect near 1.3, area). ELK spacing options are set on every compound node, because ELK doesn't inherit them.
23. **One structured `Diagram` for the page and the viewer.** `buildDiagram` returns per-frame/card/connector SVG fragments with geometry, plus a legend *data model* (`buildLegend`, with filter keys). The static page composes it; the viewer renders one Svelte `<g>` per item around the same fragments (`{@html}` works inside `<svg>`), so the two never drift. `override` on `buildDiagram`/`renderView` post-processes the layout: the hook for a future pins/sidecar file. The viewer is a prerendered `adapter-static` route that works offline; ELK runs in the browser. Filter and highlight state is a pure module (`viewer/state.ts`) with tests.

## 2026-10-21 — Phase 3 (guided review tours)

24. **Tours are model data, and a step is a viewer state plus narration.** `model.tours[]` holds `{id, title, summary?, steps[]}`. A step names its `view` and then only the state a reviewer could reach by hand: `focus[]` (spotlight; a frame lights its subtree), `select`, `highlight` (legend keys: `patterns`, `change`, `enforcement`, `proposed`), `path[]` (ordered relationship ids), `notes[]` (note ids), `onlyChanges` and `dimOthers` (default true when anything is lit). `stepFilter` turns a step into the viewer's existing `FilterState`, and `#tour=<id>&step=<id>` is a deep link like the others, so there is no parallel mechanism. In the viewer, a step card replaces the notes column. ←/→ step, Esc exits, and the camera glides to the lit bounds (instant with `prefers-reduced-motion`). Any hand interaction (legend key, selection, tab, Only changes) marks the step as *explored* and offers "Back to this step". Legend keys temporarily override the step's lighting. Several tours are allowed; one `review` tour is expected.
25. **Tours are checked like the model.** Every reference must exist and be visible in the step's view (`unknown-ref`, `tour-not-in-view`, `unknown-view`, …, as errors). A `path` must be contiguous: each connector starts where the previous one ended, or at an ancestor or descendant of it. An intentional gap is written `{ "jump": true, "text": "submit" }`; an unmarked gap warns `tour-path-gap`. Lint `tour-coverage` (default warning; `lint.tourCoverage`) lists every new, modified or removed element, proposed-pattern element, risk note and divergence (element or connector) that the tour does not *point at* (revised in 27). Coverage runs only on models without errors. Notes are referenced by `id`; unnamed notes are keyed `note:<n>`.
26. **Static tours for review without the viewer.** `c4ish tour` writes one page SVG per step (`NN-<step>.svg`, + PNG), a dependency-free `index.html` slideshow (←/→, a hash per step) and `tour.md`. A step page is the normal page. The review-focus card becomes a caption ("TOUR · n / N · title" plus narration), unlit items dim to 0.16, notes the step does not name drop to 0.35 (revised in 27), and the path is a soft blue glow with numbered blue badges placed clear of cards and labels. **Tour blue (`#2563eb`) is reserved** for tour path, badges, the selection ring and the step card. The ink callout discs stay ink, so path order and note numbers can't be confused. Layout and routing are never changed by a tour.

## 2026-10-21 — Phase 3b (owner follow-up)

27. **Coverage is strict and per tour.** Each tour must cover every review item on its own; there is no union across tours. An item counts as covered only when a step points at it:
    - `focus` or `select` covers the element itself (a frame's children are not covered) or a connector with its two endpoints;
    - a `path` covers its connectors, their endpoints and the frames those endpoints sit in;
    - a named note in `notes` covers the note and its target.
    
    Highlights (change state, pattern, proposed, enforcement) and "only changes" still light overview steps but never count. The lint message names the tour and says so. The CLI prints coverage per tour. Static pages dim every note a step does not name, including when it names none. Path badges keep a readable size: static pages scale them with page size (×1 up to 1200×1000, at most ×2); the viewer scales them with 1/zoom (at most ×3).
28. **`c4ish view` and live reload.** `c4ish view <model> [--profile] [--tour [id]] [--step id] [--port n] [--no-open] [--rebuild]` serves the prebuilt static viewer with `node:http`. It builds `build/` once if missing, and the package ships `build/`. The model and profile are served at `/__c4ish/{model,profile}.json`, and change events go out as server-sent events from `fs.watch`, which watches directories because editors replace files on save. The viewer gained a generic `?src=&profile=&live=&name=` loader. On a change it re-fetches and keeps the view, selection, tour step and camera. No new dependencies.
29. **PNGs are never committed.** `*.png` is gitignored. Committed outputs are SVG, `index.html` and `tour.md`, and `tour.md` embeds the step SVGs. `--png` remains for local use.

## 2026-11-17 — Packaging and authoring reference

30. **A Nix package, so other repositories can call the CLI.** `nix/package.nix` builds the library, CLI and static viewer with pnpm and installs only the runtime dependencies; the flake exposes it as `packages.<system>.default`. The build's install check runs the installed CLI from outside the source tree. The dev shell is unchanged.
31. **The authoring reference ships with the tool.** `docs/AUTHORING.md` is the short reference for whoever writes a model, with one complete example on the default profile; a test validates that example. `c4ish guide` prints it and `c4ish schema [model|profile]` prints the JSON Schema, so an agent in another repository needs no checkout.
32. **Schema version is pinned by the tool version.** A model states `schemaVersion` and a profile `profileVersion`; a build accepts exactly one of each and `c4ish --version` reports them, read from the shipped schema. A consumer pins the tool revision (a flake lock) and with it the schema. A breaking schema change bumps the number.

## 2026-11-17 — Code references

33. **An element can name the code it stands for.** `code` on an element or a part lists references: `path`, `path#Name` or `path#Outer.Inner`, relative to the repository root. It replaces the undocumented `sources`, so the model schema is now version 1. Nothing is drawn from it.
34. **A reference is a name, resolved by parsing.** No line numbers or syntax-tree nodes are stored. `c4ish code` parses with tree-sitter (`web-tree-sitter` and prebuilt `.wasm` grammars) for TypeScript, TSX and JavaScript. The grammars come from dev dependencies and are copied to `grammars/` at build, so the package has no native code and the Nix dependency hash is the same on every platform. Any other file takes a whole-file reference; a name into one is an error.
35. **A name is the full chain of named definitions around it.** Unnamed wrappers (call arguments, arrow functions) are skipped, and an unnamed `export default` is `default`. Only the full name resolves; when a short one fails, the error suggests it. A search by short name could later pick a different definition without anyone noticing.
36. **The extent is the whole statement:** `export`, `declare`, decorators and a lone `const` included. Comment lines directly above, with no blank line between, are outside it and reported as the definition's `comment`. A change there is `commentChanged`, not `modified`. A comment that trails code on the line above doesn't count.
37. **One name declared several times in one scope is one definition with several extents:** overloads, a value and a type, a getter and a setter, merged interfaces. The same dotted name in two different scopes is ambiguous and fails.
38. **Changed is decided by text and placed by lines.** A reference is `added`, `removed`, `modified` or `unchanged` by comparing the definition's text at the base commit and in the working tree, so a move within the file is unchanged. Separately, every changed line (`git diff -U0 --no-renames`, plus untracked files) is listed with the references that contain it, innermost first. Removed lines are placed by the extents at the base and added lines by the extents in the working tree. A whole-file reference therefore owns what the named references into that file don't.
39. **Renames and moves are not followed.** A reference to where a definition was stops resolving. The report hints at a rename in place (same text under a new name) or a move (the same name, new in another changed file; for a whole file, an added file with the same content). The model is corrected by hand, so the change stays visible to a reviewer.
40. **"Built from" goes one file deep.** `changedThrough` lists changed top-level definitions of the same file that a definition uses, directly or through other top-level definitions. Uses are matched by identifier text, so a local name that shadows a top-level one over-reports. Definitions imported from other files are not followed.
41. **The report states facts and knows no process.** It carries each owner's change state as written and compares nothing with it; comments are located, not read. The command fails only when a reference cannot be used as written: malformed, ambiguous, a name into an unparsed file type, or resolving at neither end.

## 2026-11-18 — Comparing two versions of a model

42. **Two versions are compared by id.** `c4ish diff` matches elements, relationships, contracts, absences, proposed patterns, views and tours by id, never by position or title, and reports each as added, removed or changed. A changed item lists every property that differs, with its value before and after. Ids therefore must not change between versions.
43. **Members are matched by name as well.** A field or index by its id; a tie by its id, or else its pair of fields; a part by its id, or else its title; a contract clause by its name. Parts gain an optional `id` for this. A name used twice inside one element is now a validation error (`duplicate-id`). A note without an id is matched by what it is on, its kind and its rank among those.
44. **Every difference has an aspect:** structure, text, code, presentation or provenance. The table is in `src/lib/model/diff.ts` and names every property in the schema; a test fails when a schema property is missing from it. At run time an unlisted property counts as structure, so nothing new escapes comparison by default.
45. **What is equal.** Order is ignored for items, members and set-like lists (further patterns, libraries, code references); the fields of an index keep their order. A missing `patternFit` equals `full`. A `null` pattern (deliberately none) differs from a missing one.
46. **The comparison states facts and knows no process.** It does not say which differences are allowed. A risk or question note is structure and a plain remark is text, because tour coverage already treats the first as review items. `--only` filters by aspect; the exit code does not depend on whether anything differs.
47. **A tour of what differs is a model.** `--out` writes the later version with its tours replaced by one generated tour: an overview, then one step per differing element, relationship, contract, proposed pattern, absence and note, each shown in the first view that draws it. A contract, proposed pattern, absence or note that is gone cannot be drawn, so its step says what it was and spotlights where it was (elements and relationships: 48). Differences in views, tours and the model's own fields are listed in the overview only. Writing a model, instead of adding a mode to the viewer, keeps `view` and `tour` unchanged.
48. **A dropped element or relationship is drawn.** Reading that something is gone is weaker than seeing it gone, in its place, among its neighbours. The review model puts each one back from the earlier version, marked `revision: "removed"`: after the element that preceded it, inside its former parent, in the views that listed it. It is drawn like a removed item but in red, with a `DROPPED` badge in place of the change badge, and has its own key row. "Dropped" is a different word on purpose: `removed` is a change state (the change deletes this code); dropped means the later version of the model no longer has the item. A dropped item keeps no reference to a pattern or contract that is gone too. If putting the items back gives a model that does not validate, none is put back and the steps fall back to words. `revision` is written by the tool only, and is presentation in a comparison.

## 2026-11-18 — Scenarios, bespoke elements, kind categories, reference implementations

49. **Scenarios are ids and titles, walked by tour steps.** `scenarios` on a model lists what the change must make possible; a step names the ones it walks in its own `scenarios`, and the tour card, the slideshow, the step SVG and `tour.md` show them under the narration. A scenario that no step of any tour names is reported as `scenario-coverage`, with the severity of `rules.tourCoverage`, also when the model has no tour. Unlike item coverage it is judged across all tours, because a scenario is shown once, not once per audience. The model holds no steps, actors or expected results: that text lives with the plan, and a second copy here would drift.
50. **Bespoke is a state of its own, with a reason.** `bespoke: "<why>"` on an element or a part says it is a one-off that follows no pattern on purpose. It stands in place of `pattern`: together with a pattern, with `pattern: null` or with `patternFit` it is an error, and an empty reason is an error. `pattern: null` keeps its meaning (no pattern applies, nothing to justify) and its faint drawing; bespoke is drawn to be seen (VISUAL_SPEC). Tour coverage counts an element that is bespoke, or holds a bespoke part, when its change state is new or modified (the part's own state, else its element's); an existing one-off shown as context is not a review item. `highlight.bespoke` lights them all. In a comparison, becoming or ceasing to be bespoke is structure and rewording the reason is text.
51. **A part states its fit too.** `patternFit` on a part works as on an element and is drawn with the same half disc.
52. **An element kind states its category:** `container`, `code`, `data` or `product`, or none. The default profile marks `system`, `container` and `store` as containers, `component` as code, `data` as data, and `product`, `version`, `configuration` and `page` as product concepts. c4ish uses it for one lint: a new or modified element of a code or data kind that states neither a pattern (or `null`) nor bespoke, on itself or on each of its parts, is reported as `missing-pattern` (`rules.missingPattern`, default warning). Other tools read the category from the resolved profile instead of keeping their own list of kinds.
53. **A pattern can name its reference implementation.** `code` on a pattern, in a profile or in `proposedPatterns`, takes code references. `c4ish code <profile.json>` resolves the ones in a profile and, with `--base`, says what changed in each; it lists no changed lines, since a catalog owns only its reference implementations. A model's report does not include them: there a reference implementation is ordinary code, owned by whichever element names it.
54. **`c4ish profile` prints the profile as c4ish reads it.** With a file, that file checked and merged over the default it extends; without one, the default. A caller that needs kinds, categories, change styles or relationship kinds reads them from this output and cannot drift from the tool.
55. **The command exits only after its output is out.** A report read through a pipe was cut short when it was longer than the pipe holds, because the process exited with output still queued; a file or a terminal never showed it. The exit now waits for both streams. A test reads a long report through a pipe.

## 2026-11-19 — Names inside a Svelte component

56. **A Svelte component's names are those of its script blocks.** `path.svelte#name` resolves a definition in the instance or the module script, by the same rules as a TypeScript file and on the lines it has in the component. No Svelte grammar is used: the script blocks are found with the expression Svelte's own preprocessor uses, everything outside them is blanked in place, and the result is parsed as TypeScript when a block says `lang="ts"`, else as JavaScript. Markup and styles have no names, so a change there is inside no named reference; a whole-file reference on the same element owns it. Snippets are not named: they are markup, and finding where one ends needs a parser for markup.

## 2026-11-19 — Names for code that declares nothing, layout, and the two ends of a comparison

57. **A name segment has one written form.** A name with a character the syntax uses (`.`, brackets, parentheses, a quote, a space) is written `['name']`; before this, the key `'a.b'` and the nested `a: { b }` read the same. The bracketed form of a plain name folds to the plain one, so a definition has exactly one name. When the dotted form names nothing and the bracketed one exists, the report suggests it.
58. **An array entry is named by a property of it.** An object in an array literal is `LIST[key='text']` or `LIST[key=3]`, for every property whose value is a string or number literal, so the model chooses the property that tells entries apart; a property shared by several entries names them all, as one definition with several extents. An index was rejected: it names a different entry as soon as one is inserted above. What an entry holds goes under its first literal property only, to keep one name for it. An entry with no literal property stays an unnamed wrapper, as before.
59. **A call statement is named by the first text it is given.** A statement that is a call, or a chain of calls, is `callee('text')` for the first call in the chain whose first argument is a string and whose callee is a plain chain of names. This names routes, commands and tests, which declare nothing, and gives what their callbacks hold a name that no longer collides across statements. A call given no text, or whose callee is itself computed, has no name. A case of a switch is `case('value')` under the same rule: a literal that labels a piece of code.
60. **Layout is not a change.** Where the file is parsed, two texts whose syntax trees and token texts are the same are `unchanged`, with `layoutChanged: true`; white space inside a string, a template, a regular expression or a comment's line still counts, and so does a line break that alters the tree. The comparison is of trees, not of text with white space removed, so it cannot hide a change the language sees. A file with no parser is compared as text, and so is a whole component, whose markup is not parsed. The comment above a definition is compared without its indentation. `changedThrough` uses the same comparison.
61. **`--head` names the later end.** The comparison was always base against the working tree, so anything committed later, uncommitted or untracked leaked into a report on an earlier change. `--head <commit>` reads that commit instead; the report then carries `head`. Without `--base` it resolves the references as of that commit.
62. **A removed element is not looked for without a base.** Its code is not at the head, and with no base there is no other place to look, so its references are reported as not found, with the reason, and are no problem. This holds only when everything that carries the reference is removed; a part with no change state of its own has its element's. With a base, nothing changes: the code must be at the base.
63. **A profile says which catalogs it replaces.** `extends: "default"` only added, so a project with its own pattern catalog still carried the built-in sample patterns, and a model could use one that the project never defined. `replaces` lists the catalogs (`patterns`, `patternFamilies`, `elementKinds`, …) that hold only the profile's own entries; the rest still come from the default. A pattern whose family is not in the profile is now an error in the profile (`unknown-pattern-family`); until this it was accepted without a word, and only a proposed pattern in a model was checked. It is a list of catalogs rather than a way to delete single entries: a project owns a catalog whole or builds on the built-in one.

## 2026-11-22 — The viewer on a phone

64. **Below 1000px wide there is no room beside the diagram, so the columns float over it.** At `max-width: 999px` the viewer no longer lays out a left column, a canvas and a right column (on a 390px phone that gave the diagram a column 0px wide). The title, review focus and key open from ☰ as a panel over the diagram and start closed; the picker, **Only changes** and **Export SVG** sit in a ⋯ menu; the toolbar wraps to two rows in portrait and one in landscape. One sheet is shown at a time at the bottom of the canvas: the step card, the details of what the reader picked, or the notes. In a tour the card's header folds it to a bar (`▴ n / N · title`, with Prev, Next and Hide), **Hide** leaves a small `▴ n / N` button over the whole diagram, and that button brings the card back. A step's own `select` keeps the card; the reader's tap shows details in the same place, and closing them returns to the card. From 560px wide (a phone in landscape) the card floats in the bottom-right corner. The same components are rendered in the same order as on a desktop, and every compact rule is keyed on `.viewer.compact`: at 1280×800 the page is byte-identical to before, outside a tour and in one.
65. **A step is framed in the part of the canvas the sheet leaves free.** That part is the *stage* (`stage` on `DiagramCanvas`; not given on a desktop, where the whole viewport is framed as before), and Fit, the zoom buttons and a tour step frame it. So the card does not cover what a step is about: in the example and in the clarity project review, every step that lights anything was measured with all of it inside the stage, in portrait and in landscape. Folding the card leaves the camera as it is; bringing the card back frames the step again. Turning the phone between portrait and landscape frames the step again, or fits the diagram outside a tour, only while the reader has not panned or zoomed since the viewer last framed it (`onusercamera`). A browser bar that hides itself resizes the page too, and must not disturb a pinch.
66. **Two fingers pan and pinch from a baseline.** `pinchCamera` takes the two pointers and the camera as they were when the pair took over: the zoom is the ratio of the spreads, kept to 0.1–4, and the midpoint stays put. A finger joining or leaving therefore re-bases where it is, without a jump, and a zoom limit leaves no drift to undo. `gesture.ts` is the pointer state machine, free of the DOM and tested; a tap (3px) is not a pan, and the click that ends a moved gesture is not a selection. Chrome's account of one finger lifting while the other stays is that the finger that *stays* went up, and is announced again under a new pointer id where it is or just was; the finger that left goes quiet until the whole touch ends. A pointer that goes down within 40px of a finger in the gesture, or of where one just left, is that finger again: the gesture carries on with it alone, and the pointer it displaced is taken back if it turns out to move, which also covers a browser that keeps ids. A pinch relies on the canvas's `touch-action: none`, not on `preventDefault`. Mouse drag, wheel, trackpad, the zoom buttons and Fit are unchanged: in the browser check every one of their measurements is the same before and after. The pinch was verified with synthetic touch events in headless Chrome only; its feel, Safari's own page zoom and a `pointercancel` from a system edge gesture are for a real device.
67. **The page is sized for a phone.** The viewer is `100dvh` tall. Controls take `touch-action: manipulation`, so a double tap does not zoom the page, and are 36–44px high. While compact, the root has `overscroll-behavior: none`, so a drag that runs off the canvas neither rubber-bands nor pulls to refresh. `src/app.html` is unchanged.

## 2026-11-23 — Code in git submodules

68. **A submodule is read through its pointer.** A root commit holds a submodule as one pointer, so `git diff` and `git cat-file` in the root saw one changed line and no files, and every reference into a submodule failed at a commit. A path under a submodule is now read from the submodule's own repository at the commit the root commit points to (`git ls-tree -r`, mode 160000; the index for the working tree). The reference is still written from the root, so one model can name code in several repositories.
69. **A pointer is not a change; what is behind it is.** The root's diff drops pointer entries. Each submodule is compared between the commits the two ends point to, or with the working tree as head against its own working tree and untracked files, and its paths get the submodule's path in front. A submodule new since the base is compared with the empty tree. With a head commit, only a moved pointer is compared; with the working tree, every checked-out submodule is, since a checkout can differ from its pointer.
70. **A submodule that is needed and cannot be read is a problem, never an empty result.** Needed means a reference points into it or its pointer moved. Not checked out, or a commit pointed to that is not in its local repository, is reported on the submodule and on each reference into it, and counts in `problems`. Reporting no changes for code that could not be read would let a check pass on nothing. A submodule that is not needed is not mentioned.
