# c4ish — design decisions

A dated log; later entries can supersede earlier ones. See [`DESIGN.md`](DESIGN.md) for the current design.

## 2026-10-21 — Founding decisions

1. **Purpose: review of a planned change.** The primary user is a human approving a proposed change quickly. Agents author models; humans read diagrams.
2. **Versioned JSON is canonical.** Diagrams are rendered from the model. A hand-edited diagram is never the source of truth. Layout adjustments live in a separate sidecar file, not in the model.
3. **C4-inspired, not C4-strict.** Levels go beyond C4: system → container → component → data → field. Libraries used inside a component are first-class.
4. **Product and engineering in one model.** One change can show what changes for the user and how it is built, as two views with a mapping between them.
5. **Notation carries meaning, and is data.** Projects define element types, relationship kinds, enforcement levels and visual notation in a profile. c4ish ships a generic default. Core rules: structure is nesting, reference is a connector; every connector states its enforcement; line style carries meaning without colour; colour means one thing per view.
6. **Change state everywhere.** New, modified, reused and removed are core, not decoration. Removed items stay visible.
7. **Patterns are references, not content.** An element names its project pattern (type/variation). c4ish links to the catalog but doesn't store pattern content.
8. **Throwaway models.** A model is scoped to one change. No whole-system inventory.
9. **Rendering and layout first; model editing later.** v0 renders, auto-lays out and lets the user adjust the layout. Editing the model in the viewer is deferred.
10. **Library-first, single repository.** Svelte 5 + TypeScript library with a small SvelteKit viewer in `src/routes`, a CLI for agents, Nix for tools, pnpm for dependencies.

## 2026-10-21 — Phase 1 (v0 implementation)

11. **ELK first, TALA later.** Layout goes through a `LayoutEngine` interface (`src/lib/layout/types.ts`). It returns absolute rects, edge polylines and label boxes. v0 ships an elkjs implementation: layered, `INCLUDE_CHILDREN` for compound nodes, orthogonal routing, fixed-side ports for fields, inline edge labels. elkjs is pure JS, so it builds reproducibly and runs in Node and the browser. A TALA adapter and pinned positions (`LayoutNodeInput.fixed`) fit the same interface. Supersedes "TALA is the first candidate" in DESIGN §4.
12. **Pure-TypeScript SVG renderer, no headless browser.** The renderer emits an SVG string and doesn't depend on the DOM. The CLI, tests and the SvelteKit demo all use the same code (`{@html}` in Svelte). This answers PLAN open question 3. Svelte components for an interactive viewer can wrap the same scene later.
13. **Deterministic text metrics.** Text is measured from Noto Sans advance widths baked into `src/lib/text/metrics.ts` (generated from `@fontsource/noto-sans`), with a 3% safety margin. The font stack is `'Noto Sans','Inter','Segoe UI',system-ui`. The same model gives byte-identical SVG on every machine (tested).
14. **Change state is hue-free.** New = ink header band; modified = light slate band; reused = muted; removed = dashed grey with strikethrough. Each also gets a text badge. Hue is left for the one per-view meaning (enforcement or area). See VISUAL_SPEC §4.1.
15. **Only data relationships are coloured by enforcement.** Runtime calls are quiet slate even when the model states an enforcement level. Colouring every connector amber made "our code" the dominant colour and hid the few relationships that carry integrity. Lint still requires enforcement on data kinds (`enforcementRequired`).
16. **Top-down by default for engineering and product views.** In layered left-to-right layouts, real models came out 3–4× wider than tall. Top-down reads as a page: UI, then backend, then data, with notes beside it. Views can still set `direction`.
17. **Text is split into title / subtitle / details.** Titles have a budget of 40 characters and subtitles 64 (lint). A subtitle wraps to two lines. Details become lettered footnotes, and contracts become C1… footnotes. Nothing is lost, and the diagram stays scannable.
18. **`include` means "these subtrees".** A listed element brings in its ancestors (as frames) and its descendants. `exclude` removes subtrees; element-level `views` restricts further.

## 2026-10-21 — Phase 2 (visual iteration and viewer)

19. **Card colour = pattern, line colour = who enforces.** The owner could not tell patterns apart from a glyph and a chip. Engineering views now use two separate hue channels: the card (header tint, 7px left band, icon, caps pattern label) takes `PatternDef.colour`, falling back to the family colour; data connectors keep the enforcement colours. Pattern colours avoid rose and amber, which belong to enforcement. Proposed patterns keep the hatch (band and header). The key states both mappings in words. Lint `colour-meaning` now only warns about a *pattern* + *relationship kind* pair, which really does compete for hue. Supersedes "hue for patterns by default" in VISUAL_SPEC §10 and refines 14.
20. **Change state lives on the badge and border, not the header.** The header belongs to the pattern now. New gets a solid ink badge and a 1.5 ink border; modified gets an outlined badge; reused is drawn at 50% opacity with a thin grey border; removed is dashed slate, struck through, with a solid badge. Reused context recedes, so changes, proposals and risks stand out. Still hue-free (14).
21. **Diagram-first page.** The page holds the title, review focus, diagram, and a right column with numbered notes and a compact key. Details and contracts are no longer printed as footnotes. `render --appendix` writes `<out>.appendix.md` (notes, lettered details, connector details, contracts), and the viewer shows them in a side panel. Fonts are larger (node title 14.5, label 11.5). Supersedes the footnote half of 17.
22. **We place connector labels after routing; `direction: 'auto'`.** ELK routes without labels. `placeLabels` then tries positions along each polyline (on the line or beside it) and penalises overlap with cards, frame headers, other labels and crossings. If labels still collide, the layout is retried with more layer spacing. `direction: 'auto'` (the default profile) lays out top-down and left-to-right and keeps the lower `layoutScore` (bends, length, aspect near 1.3, area). ELK spacing options are set on every compound node, because ELK doesn't inherit them.
23. **One structured `Diagram` for the page and the viewer.** `buildDiagram` returns per-frame/card/connector SVG fragments with geometry, plus a legend *data model* (`buildLegend`, with filter keys). The static page composes it; the viewer renders one Svelte `<g>` per item around the same fragments (`{@html}` works inside `<svg>`), so the two never drift. `override` on `buildDiagram`/`renderView` post-processes the layout: the hook for a future pins/sidecar file. The viewer is a prerendered `adapter-static` route that works offline; ELK runs in the browser. Filter and highlight state is a pure module (`viewer/state.ts`) with tests.

## 2026-10-21 — Phase 3 (guided review tours)

24. **Tours are model data, and a step is a viewer state plus narration.** `model.tours[]` holds `{id, title, summary?, steps[]}`. A step names its `view` and then only the state a reviewer could reach by hand: `focus[]` (spotlight; a frame lights its subtree), `select`, `highlight` (legend keys: `patterns`, `change`, `enforcement`, `proposed`), `path[]` (ordered relationship ids), `notes[]` (note ids), `onlyChanges` and `dimOthers` (default true when anything is lit). `stepFilter` turns a step into the viewer's existing `FilterState`, and `#tour=<id>&step=<id>` is a deep link like the others, so there is no parallel mechanism. In the viewer, a step card replaces the notes column. ←/→ step, Esc exits, and the camera glides to the lit bounds (instant with `prefers-reduced-motion`). Any hand interaction (legend key, selection, tab, Only changes) marks the step as *explored* and offers "Back to this step". Legend keys temporarily override the step's lighting. Several tours are allowed; one `review` tour is expected.
25. **Tours are checked like the model.** Every reference must exist and be visible in the step's view (`unknown-ref`, `tour-not-in-view`, `unknown-view`, …, as errors). A `path` must be contiguous: each connector starts where the previous one ended, or at an ancestor or descendant of it. An intentional gap is written `{ "jump": true, "text": "submit" }`; an unmarked gap warns `tour-path-gap`. Lint `tour-coverage` (default warning; `lint.tourCoverage`) lists every new, modified or removed element or connector, proposed-pattern element, risk note and divergence that no step lights, across all tours. Coverage runs only on models without errors. Notes are referenced by `id`; unnamed notes are keyed `note:<n>`.
26. **Static tours for review without the viewer.** `c4ish tour` writes one page SVG per step (`NN-<step>.svg`, + PNG), a dependency-free `index.html` slideshow (←/→, a hash per step) and `tour.md`. A step page is the normal page. The review-focus card becomes a caption ("TOUR · n / N · title" plus narration), unlit items dim to 0.16, non-spotlit notes drop to 0.35 when the step names notes, and the path is a soft blue glow with numbered blue badges placed clear of cards and labels. **Tour blue (`#2563eb`) is reserved** for tour path, badges, the selection ring and the step card. The ink callout discs stay ink, so path order and note numbers can't be confused. Layout and routing are never changed by a tour.
